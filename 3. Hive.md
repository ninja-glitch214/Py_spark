> # 1. Introduction to Apache Hive
> 
> **Apache Hive is a data warehouse system for Hadoop that allows us to query and analyze large datasets using an SQL-like language called HiveQL.**
> 
> Hive maintains metadata about data stored in HDFS and presents that data as tables, making it easier to perform data analysis.
> 
> ### Why do we need Hive?
> 
> You already know that:
> 
> - **HDFS** stores distributed data.
> - **MapReduce** processes data in parallel.
> - **Pig** provides a high-level data-flow language for describing data transformations.
> 
> Hive addresses another need: **an SQL-like way to query and analyze big data.**
> 
> For example, suppose a company stores millions of customer records in HDFS. Instead of writing a complete MapReduce program to find customers from a particular city, you can write a query such as:
> 
> ```
> SELECT *
> FROM customers
> WHERE city = 'Pune';
> ```
> 
> Hive translates the query into an execution plan that can run using an available processing engine.
> 
> ### Brain map: Where does Hive fit?
> 
> ```
>                    HADOOP ECOSYSTEM
>                           |
>              +------------+------------+
>              |            |            |
>              v            v            v
>             HDFS      MapReduce       Hive
>              |            |            |
>              |            |            v
>              |            |       HiveQL (SQL-like)
>              |            |            |
>              v            v            v
>           Store data   Process data   Query and analyze
>                                       data using tables
> ```
> 
> **Remember:** Hive doesn't replace HDFS. It provides a table-oriented, SQL-like interface for analyzing data stored in Hadoop.

> # 2. Comparing Hive with SQL
> 
> HiveQL resembles SQL because it supports familiar database operations. However, Hive is designed for distributed data processing rather than being a conventional transactional database.
> 
> ## 2.1 SQL features supported by Hive
> 
> Your PPT lists the following SQL-related capabilities.
> 
> |Category|Examples|
> |---|---|
> |Data types|`INT`, `TINYINT`, `SMALLINT`, `BIGINT`, `BOOLEAN`, `FLOAT`, `DOUBLE`, `STRING`, `BINARY`, `TIMESTAMP`, `DECIMAL`, `CHAR`, `VARCHAR`, `DATE`|
> |Complex types|`ARRAY`, `MAP`, `STRUCT`, `UNION`|
> |Selection and filtering|`SELECT`, expressions in `WHERE` and `HAVING`|
> |Grouping and sorting|`GROUP BY`, `ORDER BY`, `SORT BY`|
> |Data distribution|`DISTRIBUTE BY`, `CLUSTER BY`|
> |Data modification|`LOAD`, `INSERT`, `INSERT ... SELECT`|
> |Joins|Inner, left, right, full outer, cross, and left semi joins|
> |Advanced SQL|Subqueries, `UNION`, `ROLLUP`, `CUBE`, window functions such as `RANK()`|
> |Conditions involving subqueries|`IN`, `NOT IN`, `EXISTS`, `NOT EXISTS`|
> 
> _Note:_ Exact syntax and support can vary by Hive version.
> 
> ## 2.2 Hive versus a traditional relational database
> 
> |Traditional RDBMS|Hive|
> |---|---|
> |Commonly designed for transactional applications|Primarily designed for analytical queries|
> |Often works with database-managed tables and storage|Commonly queries files stored in HDFS or compatible storage|
> |Supports low-latency transactions in suitable systems|Traditionally optimized for large-scale batch analytics|
> |Uses SQL|Uses HiveQL, which is SQL-like|
> |Database engine manages query execution|Hive plans queries for execution on a supported processing engine|
> 
> **Key idea:** Hive allows users familiar with SQL to analyze large datasets without manually implementing every processing operation using MapReduce.
> 
> # 3. Hive Architecture
> 
> Hive acts as a layer between the user writing a query and the distributed processing system executing it.
> 
> The PPT includes a Hive architecture diagram, although its component labels are not available in the extracted text. The following is the standard conceptual architecture that connects Hive to the Hadoop components you've studied.
> 
> ## 3.1 Architecture diagram
> 
> ```
>              USER / APPLICATION
>                      |
>                      v
>               HiveQL Query
>                      |
>                      v
>        +---------------------------+
>        | Client Interface          |
>        | CLI / Beeline / Application|
>        +---------------------------+
>                      |
>                      v
>        +---------------------------+
>        | HiveServer2               |
>        | Accepts client requests   |
>        +---------------------------+
>                      |
>                      v
>        +---------------------------+
>        | Driver                    |
>        | Manages query lifecycle   |
>        +---------------------------+
>                      |
>                      v
>        +---------------------------+
>        | Compiler / Optimizer      |
>        | Parses and plans query    |
>        +---------------------------+
>               |             |
>               |             v
>               |       Metastore
>               |       (Metadata)
>               v
>        Execution Plan
>               |
>               v
>        Processing Engine
>        (e.g. MapReduce)
>               |
>               v
>              HDFS
>        (Actual data files)
>               |
>               v
>        Query Results
> ```
> 
> ## 3.2 Important components
> 
> |Component|Function|
> |---|---|
> |**Client interface**|Lets users submit HiveQL queries|
> |**HiveServer2**|Accepts requests from clients and manages sessions|
> |**Driver**|Coordinates the query's lifecycle|
> |**Compiler**|Parses the query and creates an execution plan|
> |**Optimizer**|Improves the plan to make execution more efficient|
> |**Metastore**|Stores metadata about tables, columns, partitions, and data locations|
> |**Execution engine**|Executes the plan using a supported processing framework|
> |**HDFS**|Stores the underlying data files|
> 
> ### The most important distinction: Metastore versus HDFS
> 
> Imagine a Hive table named `customers`.
> 
> - **HDFS stores:** the actual customer data.
> - **Hive Metastore stores:** the table's metadata, such as column names, data types, partition definitions, and storage location.
> 
> For example:
> 
> ```
> Hive Metastore
>       |
>       | customers table
>       | Columns: id, name, city
>       | Location: /warehouse/customers
>       |
>       v
> HDFS: /warehouse/customers
>       |
>       v
> Actual customer data files
> ```
> 
> The Metastore doesn't normally contain the complete customer dataset. It contains information that helps Hive interpret and locate the data.
> 
> ### How a Hive query executes
> 
> Suppose you run:
> 
> ```
> SELECT city, COUNT(*)
> FROM customers
> GROUP BY city;
> ```
> 
> The conceptual process is:
> 
> 1. The client submits the query.
> 2. Hive parses and validates the query.
> 3. Hive obtains table metadata from the Metastore.
> 4. Hive creates and optimizes an execution plan.
> 5. The execution engine processes the required data.
> 6. Hive returns the results to the client.
> 
> In a classic MapReduce-based Hive deployment, the plan may generate MapReduce jobs. Newer Hive deployments can use other execution engines.
>

> # 5. Defining Hive Tables
> 
> Hive presents data as tables, similar to relational databases. A table definition specifies the columns, data types, and how Hive interprets the underlying data.
> 
> The PPT covers managed tables, external tables, and specifying a table's location. Day11-13
> 
> ## 5.1 Creating a managed table
> 
> A managed table is also called an **internal table**.
> 
> Example based on the PPT:
> 
> ```
> CREATE TABLE customer (
>     customerID INT,
>     firstName STRING,
>     lastName STRING,
>     birthday TIMESTAMP
> )
> ROW FORMAT DELIMITED
> FIELDS TERMINATED BY ',';
> ```
> 
> ### Explanation
> 
> - `CREATE TABLE customer` creates a table named `customer`.
> - `customerID INT` defines an integer column.
> - `firstName STRING` and `lastName STRING` define text columns.
> - `birthday TIMESTAMP` defines a timestamp column.
> - `ROW FORMAT DELIMITED` specifies a delimited row format.
> - `FIELDS TERMINATED BY ','` specifies comma-separated fields.
> 
> For example, a row in the input file could look like:
> 
> ```
> 101,Rahul,Sharma,2002-04-15 00:00:00
> ```
> 
> Hive uses the table schema to interpret each field.
> 
> ### Managed table behaviour
> 
> In a managed table, Hive manages the table's data and metadata.
> 
> ```
> CREATE TABLE students (
>     id INT,
>     name STRING
> );
> ```
> 
> **Important:** Dropping a managed table normally removes its table data as well as its metadata. Exact behaviour depends on the table's storage configuration and environment.
> 
> ## 5.2 Creating an external table
> 
> An **external table** lets Hive access data stored at a specified location without treating the data as fully managed by the table.
> 
> Example from the PPT:
> 
> ```
> CREATE EXTERNAL TABLE salaries (
>     gender STRING,
>     age INT,
>     salary DOUBLE,
>     zip INT
> )
> ROW FORMAT DELIMITED
> FIELDS TERMINATED BY ',';
> ```
> 
> This defines the table's schema and tells Hive that the fields are comma-delimited.
> 
> ### Managed versus external tables
> 
> |Feature|Managed table|External table|
> |---|---|---|
> |Data ownership|Hive manages the table's data|Data is treated as externally managed|
> |Metadata|Stored in the Metastore|Stored in the Metastore|
> |Dropping the table|Normally removes data and metadata|Normally removes metadata while preserving external data|
> |Typical use|Data managed within a Hive warehouse|Data shared with or managed by other systems|
> 
> External-table behaviour can vary with Hive versions and table properties. The main distinction to learn is how Hive manages the underlying data when a table is dropped.
> 
> ## 5.3 Specifying a table location
> 
> You can specify where an external table's data is located using `LOCATION`.
> 
> Example from the PPT:
> 
> ```
> CREATE EXTERNAL TABLE salaries (
>     gender STRING,
>     age INT,
>     salary DOUBLE,
>     zip INT
> )
> ROW FORMAT DELIMITED
> FIELDS TERMINATED BY ','
> LOCATION '/user/train/salaries/';
> ```
> 
> Here, Hive associates the `salaries` table with the specified location in the Hadoop filesystem.
> 
> The relationship is:
> 
> ```
> Hive table: salaries
>        |
>        v
> Metastore stores schema
> and location information
>        |
>        v
> /user/train/salaries/
>        |
>        v
> Underlying data files
> ```
> 
> This is especially useful when data already exists in HDFS and you want Hive to query it without first creating a separate copy.
>

> # 6. Loading Data into Hive
> 
> The PPT demonstrates three ways to populate a table: loading a local file, loading a file from HDFS, and inserting query results into another table. Day11-13
> 
> ## 6.1 Load a local file
> 
> ```
> LOAD DATA LOCAL INPATH '/tmp/customers.csv'
> OVERWRITE INTO TABLE customers;
> ```
> 
> - `LOCAL` means the source file is on the machine from which the Hive operation accesses local files.
> - `INPATH` specifies the source file.
> - `OVERWRITE INTO TABLE` replaces the existing table data with the loaded data.
> 
> In many conventional Hive deployments, the local file is copied into the table's storage location.
> 
> ## 6.2 Load a file from HDFS
> 
> ```
> LOAD DATA INPATH '/user/train/customers.csv'
> OVERWRITE INTO TABLE customers;
> ```
> 
> Here, the source file is already in the Hadoop filesystem.
> 
> **Difference:**
> 
> ```
> LOCAL INPATH
>     → Source is a local filesystem path
> 
> INPATH without LOCAL
>     → Source is a Hadoop filesystem path
> ```
> 
> The exact load behaviour depends on the storage system and Hive version.
> 
> ## 6.3 Insert query results into a table
> 
> The PPT demonstrates inserting selected customer records into a `birthdays` table:
> 
> ```
> INSERT INTO TABLE birthdays
> SELECT firstName, lastName, birthday
> FROM customers
> WHERE birthday IS NOT NULL;
> ```
> 
> Explanation:
> 
> 1. Read records from `customers`.
> 2. Select `firstName`, `lastName`, and `birthday`.
> 3. Exclude rows where `birthday` is `NULL`.
> 4. Insert the selected results into `birthdays`.
> 
> ### `INSERT INTO` versus `INSERT OVERWRITE`
> 
> |Command|Behaviour|
> |---|---|
> |`INSERT INTO TABLE`|Adds results to the existing table data|
> |`INSERT OVERWRITE TABLE`|Replaces the existing table data with the query results|
> 
> This distinction matters when rerunning a query.

> # 7. Performing Queries in Hive
> 
> Once a table is defined and its data is accessible, you can use familiar SQL operations to query it.
> 
> ## 7.1 Retrieve all records
> 
> Example from the PPT:
> 
> ```
> SELECT *
> FROM customers;
> ```
> 
> `*` selects all columns.
> 
> ## 7.2 Select specific columns, filter, and sort
> 
> ```
> SELECT firstName, lastName, address, zip
> FROM customers
> WHERE orderID > 0
> ORDER BY zip;
> ```
> 
> This query:
> 
> 1. Reads records from `customers`.
> 2. Filters records using `WHERE`.
> 3. Selects the four specified columns.
> 4. Orders the final result by `zip`.
> 
> The example assumes the referenced columns exist in the table schema.
> 
> ## 7.3 Join two tables
> 
> Example from the PPT:
> 
> ```
> SELECT customers.*, orders.*
> FROM customers
> JOIN orders
>     ON customers.customerID = orders.customerID;
> ```
> 
> This joins customer records with matching order records.
> 
> The join condition:
> 
> ```
> customers.customerID = orders.customerID
> ```
> 
> matches records using the customer ID.
> 
> ### Common join types
> 
> |Join|Purpose|
> |---|---|
> |`INNER JOIN`|Returns matching records from both tables|
> |`LEFT JOIN`|Returns all left-table records and matching right-table records|
> |`RIGHT JOIN`|Returns all right-table records and matching left-table records|
> |`FULL OUTER JOIN`|Returns matching records and unmatched records from both sides|
> |`CROSS JOIN`|Produces combinations of records from both tables|
> |`LEFT SEMI JOIN`|Returns left-table records that have a match on the right|

> # 8. Hive Partitions
> 
> **Partitioning divides a table's data into separate directories based on the values of one or more specified columns.**
> 
> It helps Hive avoid scanning irrelevant data when a query filters on a partition column.
> 
> ## 8.1 Creating a partitioned table
> 
> Example from the PPT:
> 
> ```
> CREATE TABLE employees (
>     id INT,
>     name STRING,
>     salary DOUBLE
> )
> PARTITIONED BY (dept STRING);
> ```
> 
> Here:
> 
> - `id`, `name`, and `salary` are ordinary data columns.
> - `dept` is the partition column.
> 
> Suppose the departments are HR, Support, Engineering, and Training. The table's data may be organized like this:
> 
> ```
> /apps/hive/warehouse/employees/
>           |
>           +-- dept=hr/
>           |
>           +-- dept=support/
>           |
>           +-- dept=engineering/
>           |
>           +-- dept=training/
> ```
> 
> Each directory contains the data belonging to that department.
> 
> ## 8.2 How partitioning helps
> 
> Suppose you execute:
> 
> ```
> SELECT *
> FROM employees
> WHERE dept = 'engineering';
> ```
> 
> Without partition pruning, Hive might need to examine data from multiple departments.
> 
> With appropriate partitioning, Hive can often read only the `dept=engineering` partition.
> 
> ```
> employees table
>       |
>       +-- dept=hr/             Skip
>       |
>       +-- dept=support/        Skip
>       |
>       +-- dept=engineering/    Read
>       |
>       +-- dept=training/       Skip
> ```
> 
> This can reduce the amount of data scanned and improve query performance.
> 
> ### Important distinction
> 
> In the example above, `dept` is a partition column rather than one of the ordinary columns listed inside the parentheses.
> 
> When inserting data into a partitioned table, you can specify the partition explicitly:
> 
> ```
> INSERT INTO TABLE employees
> PARTITION (dept = 'engineering')
> SELECT id, name, salary
> FROM employee_source
> WHERE dept = 'engineering';
> ```
> 
> This example assumes `employee_source` contains `id`, `name`, `salary`, and `dept`.
> 
> **Remember:** Partitioning divides data according to column values, commonly creating directories such as `dept=engineering/`.
>

> # 9. Hive Buckets
> 
> **Bucketing divides table data into a fixed number of buckets using a hash function applied to a specified column.**
> 
> Unlike partitioning, bucketing does not ordinarily create one directory per distinct column value.
> 
> ## 9.1 How bucketing works
> 
> Conceptually:
> 
> ```
>              Input records
>                    |
>                    v
>           Choose bucket column
>                    |
>                    v
>            Apply hash function
>                    |
>                    v
>         +----------+----------+
>         |          |          |
>         v          v          v
>      Bucket 0   Bucket 1   Bucket 2
> ```
> 
> For example, records can be distributed into buckets based on their `customerID`.
> 
> Records with the same bucketing key are assigned consistently according to the bucketing scheme.
> 
> ## 9.2 Creating a bucketed table
> 
> Example:
> 
> ```
> CREATE TABLE customers_bucketed (
>     customerID INT,
>     name STRING,
>     city STRING
> )
> CLUSTERED BY (customerID)
> INTO 4 BUCKETS;
> ```
> 
> This specifies four buckets, with `customerID` used as the bucketing column.
> 
> ### Why use buckets?
> 
> Bucketing can help with:
> 
> - Organizing data into a fixed number of groups.
> - Some joins and aggregations when the data layout matches the query.
> - Sampling data.
> - Certain query optimizations.
> 
> However, bucketing does not automatically make every query faster. Its benefits depend on the query, data distribution, storage format, and execution engine.
> 
> ## 9.3 Partitioning versus bucketing
> 
> |Feature|Partitioning|Bucketing|
> |---|---|---|
> |How data is divided|By partition-column values|By hash of a bucketing column|
> |Number of groups|Depends on partition values|Specified when defining the table|
> |Typical layout|Separate directories, such as `dept=hr/`|Separate bucket files|
> |Main purpose|Reduce data scanned using partition filters|Organize records for suitable processing optimizations|
> |Example|Partition by department|Four buckets by customer ID|
> 
> **Brain-map connection:**
> 
> ```
> Hive table
>     |
>     +-- Partitioning
>     |      |
>     |      +-- Divide by department
>     |          hr / support / engineering
>     |
>     +-- Bucketing
>            |
>            +-- Hash customer ID
>                bucket 0 / bucket 1 / ...
> ```
>

> # 10. Skewed Tables
> 
> A table is **skewed** when some column values occur much more frequently than others.
> 
> For example, suppose a customer dataset contains ZIP codes:
> 
> ```
> 57701 → 500,000 records
> 57702 → 450,000 records
> Other ZIP codes → 1,000 records each
> ```
> 
> The first two ZIP codes are much more common than the others.
> 
> During distributed processing, heavily concentrated values can cause uneven workloads. One processing task may receive far more records than other tasks.
> 
> ## 10.1 Defining a skewed table
> 
> The PPT gives this example:
> 
> ```
> CREATE TABLE Customers (
>     id INT,
>     username STRING,
>     zip INT
> )
> SKEWED BY (zip)
> ON (57701, 57702)
> STORED AS DIRECTORIES;
> ```
> 
> Explanation:
> 
> - `SKEWED BY (zip)` identifies the column whose values have a skewed distribution.
> - `ON (57701, 57702)` identifies the skewed values.
> - `STORED AS DIRECTORIES` specifies a directory-based storage arrangement for those skewed values.
> 
> Hive can use skew-aware storage and processing strategies to handle heavily concentrated values more efficiently.
> 
> ### Partitioning, bucketing, and skew: when to think about each
> 
> ```
> Problem: Data is large
>          |
>          +-- Need to read only a department?
>          |       → Partitioning
>          |
>          +-- Need data divided into a fixed
>          |   number of hash-based groups?
>          |       → Bucketing
>          |
>          +-- Some values occur far more often
>                  than others?
>                  → Skew handling
> ```
> 
> These techniques address different problems; they are not interchangeable.
> 
> The PPT includes a demonstration on understanding partitions and skew.
>

> # 11. Sorting Data in Hive
> 
> The PPT distinguishes between `ORDER BY` and `SORT BY`. Day11-13
> 
> ## 11.1 `ORDER BY`
> 
> `ORDER BY` requests a complete ordering of the final result.
> 
> ```
> SELECT *
> FROM employees
> ORDER BY salary;
> ```
> 
> This requests records in ascending salary order.
> 
> To sort in descending order:
> 
> ```
> SELECT *
> FROM employees
> ORDER BY salary DESC;
> ```
> 
> In classic Hive execution, a global ordering generally requires coordination across the distributed processing tasks and may be more expensive for large datasets.
> 
> ## 11.2 `SORT BY`
> 
> `SORT BY` sorts data **within each reducer's output**, rather than guaranteeing one globally sorted result across all reducers.
> 
> ```
> SELECT *
> FROM employees
> SORT BY salary;
> ```
> 
> Each reducer's output is sorted by salary, but records from different reducers are not necessarily globally ordered relative to one another.
> 
> ### Difference
> 
> |`ORDER BY`|`SORT BY`|
> |---|---|
> |Requests a global ordering|Sorts within each reducer|
> |Provides globally ordered results|Does not guarantee global ordering|
> |Can require more coordination|Can be useful for distributed sorting|
> 
> **Exam point:** `ORDER BY` means global ordering; `SORT BY` means ordering within each reducer's output.
>

> # 12. Using `DISTRIBUTE BY`
> 
> `DISTRIBUTE BY` controls how records are distributed among reducers based on the values of specified columns.
> 
> It is different from `SORT BY`: distribution determines which reducer receives a record, while sorting determines the order of records within a reducer's output.
> 
> ## 12.1 Distribute records by age
> 
> Example from the PPT:
> 
> ```
> INSERT OVERWRITE TABLE mytable
> SELECT gender, age, salary
> FROM salaries
> DISTRIBUTE BY age;
> ```
> 
> This distributes records according to `age`.
> 
> Records with the same distribution key are sent to the same reducer under the standard hash-based distribution behaviour.
> 
> ## 12.2 Combine `DISTRIBUTE BY` and `SORT BY`
> 
> The PPT also shows:
> 
> ```
> INSERT OVERWRITE TABLE mytable
> SELECT gender, age, salary
> FROM salaries
> DISTRIBUTE BY age
> SORT BY age;
> ```
> 
> The two clauses serve different purposes:
> 
> 1. `DISTRIBUTE BY age` determines how records are assigned to reducers.
> 2. `SORT BY age` sorts records within each reducer's output.
> 
> This can be useful when you need records grouped by distribution key and sorted within the resulting partitions.
> 
> ## 12.3 `CLUSTER BY`
> 
> The PPT lists `CLUSTER BY` among Hive's SQL-related capabilities.
> 
> Conceptually, `CLUSTER BY column` combines distribution and sorting by the same column. It is broadly equivalent to:
> 
> ```
> DISTRIBUTE BY column
> SORT BY column
> ```
> 
> It does not guarantee that the entire output is globally sorted.
> 
> ### Brain map: Hive's sorting and distribution clauses
> 
> ```
> ORDER BY
>     → Global ordering
> 
> SORT BY
>     → Sort within each reducer
> 
> DISTRIBUTE BY
>     → Decide which reducer receives each record
> 
> CLUSTER BY
>     → Distribute and sort using the same column
> ```
>

> # 13. Storing Query Results to a File
> 
> Hive can write query results to a directory instead of storing them in a Hive table.
> 
> The PPT demonstrates two commands:
> 
> - `INSERT OVERWRITE DIRECTORY`
> - `INSERT OVERWRITE LOCAL DIRECTORY` Day11-13
> 
> ## 13.1 Store results in HDFS
> 
> Example from the PPT:
> 
> ```
> INSERT OVERWRITE DIRECTORY '/user/train/ca_or_sd/'
> SELECT name, state
> FROM names
> WHERE state = 'CA'
>    OR state = 'SD';
> ```
> 
> This query:
> 
> 1. Reads records from `names`.
> 2. Selects records where the state is California (`CA`) or South Dakota (`SD`).
> 3. Keeps the `name` and `state` fields.
> 4. Writes the results to the specified Hadoop filesystem directory.
> 
> **`OVERWRITE` means the destination's existing output is replaced.**
>

> # Joins in Hive
> 
These are **three join strategies used in Hive**. The confusing part is that _Shuffle Join, Map (Broadcast) Join, and Sort-Merge-Bucket (SMB) Join_ describe different ways Hive brings records together to perform a join.
Let's connect them to what you already know about **MapReduce, shuffle, bucketing, and sorting**.
> # 1. First, understand the big picture
> 
> Suppose we want to join two tables using `dept_id`.
> 
> **Employees**
> 
> |emp_id|name|dept_id|
> |---|---|---|
> |1|Amit|10|
> |2|Neha|20|
> |3|Ravi|10|
> 
> **Departments**
> 
> |dept_id|dept_name|
> |---|---|
> |10|IT|
> |20|HR|
> 
> The result should match each employee with their department.
> 
> The question is: **How can Hive bring matching records together efficiently?**
> 
> There are three common strategies:
> 
> ```
>                     HIVE JOIN STRATEGIES
>                             |
>              ┌──────────────┼──────────────┐
>              |              |              |
>              v              v              v
>         SHUFFLE JOIN    MAP/BROADCAST    SORT-MERGE-
>                             JOIN         BUCKET JOIN
>              |              |              |
>        Shuffle both    Send small      Use compatible
>        sides by key    table to maps   sorted buckets
>              |              |              |
>        Join at         Join during     Join efficiently
>        reducers        map phase       using sorted data
> ```
> 
> ---
> 
> # 2. Shuffle Join (Reduce-Side Join)
> 
> **Core idea: Bring matching records from both tables to the same reducer.**
> 
> This connects directly to the MapReduce shuffle process you learned earlier.
> 
> ### How it works
> 
> Suppose the employee table is large and the department table is also large.
> 
> ```
>  Employees                     Departments
>      |                               |
>      v                               v
>    Mapper                          Mapper
>      |                               |
>      └──────────────┬────────────────┘
>                     |
>                     v
>              SHUFFLE + SORT
>           Group records by dept_id
>                     |
>           ┌─────────┴─────────┐
>           v                   v
>       Reducer 1            Reducer 2
>       dept_id = 10         dept_id = 20
>           |                   |
>           v                   v
>        Perform JOIN         Perform JOIN
> ```
> 
> For example, all records with `dept_id = 10` are brought together so the reducer can match Amit and Ravi with the IT department.
> 
> ### Why is shuffle required?
> 
> The matching employee and department records might initially be stored in different files or on different machines.
> 
> The shuffle ensures that records with the same join key reach the same reducer.
> 
> **Advantages**
> 
> - Suitable for large datasets.
> - Neither table necessarily needs to fit in memory.
> 
> **Disadvantage**
> 
> - Shuffling large amounts of data across the network can be expensive.
> 
> **Remember:** Shuffle Join = Bring matching keys together through shuffle, then join.
> 
> ---
> 
> # 3. Map (Broadcast) Join
> 
> **Core idea: Send the small table to the mappers processing the large table.**
> 
> This avoids the usual reduce-side shuffle for the join.
> 
> Suppose:
> 
> - Employees: 10 million records.
> - Departments: 10 records.
> 
> Shuffling both tables would be unnecessary when the department table is so small.
> 
> ### How it works
> 
> ```
>        Small table: Departments
>                    |
>                    v
>            Broadcast/load into
>              mapper memory
>                    |
>                    v
> Large table --> Mapper
>                    |
>                    v
>           Look up department
>              using dept_id
>                    |
>                    v
>              Matched result
> ```
> 
> The department table is made available to the mappers processing employee records.
> 
> For example, the mapper processes:
> 
> ```
> Employee: Amit, dept_id = 10
>                   |
>                   v
>         Look up dept_id = 10
>                   |
>                   v
>              Department: IT
> ```
> 
> The mapper can now produce the joined record without sending the employee record through a reduce-side shuffle.
> 
> ### Why call it a Broadcast Join?
> 
> Because the small table is distributed or made available to the relevant map tasks.
> 
> Think of it this way:
> 
> - **Shuffle Join:** Bring matching records to reducers.
> - **Broadcast Join:** Bring the small table to the mappers.
> 
> ### Advantages
> 
> - Avoids the usual join shuffle.
> - Often faster when one table is small enough to fit in memory.
> 
> ### Limitation
> 
> The small table must be manageable for the chosen execution plan. If it is too large, loading it into mapper memory may cause memory problems.
> 
> ---
> 
> # 4. Sort-Merge-Bucket (SMB) Join
> 
> This one connects directly to your earlier topics: **bucketing and sorting**.
> 
> Let's first understand the three words.
> 
> |Term|Meaning|
> |---|---|
> |Sort|Records are sorted by the join key.|
> |Merge|The sorted records are scanned together to find matching keys.|
> |Bucket|Records are organized into buckets using a bucketing column.|
> 
> ### The central idea
> 
> Suppose both tables are large, so broadcasting either one is impractical.
> 
> However, both tables are already organized into compatible buckets and sorted by `dept_id`.
> 
> For example:
> 
> **Employees — Bucket 1**
> 
> |emp_id|name|dept_id|
> |---|---|---|
> |1|Amit|10|
> |3|Ravi|10|
> |2|Neha|20|
> 
> **Departments — corresponding Bucket 1**
> 
> |dept_id|dept_name|
> |---|---|
> |10|IT|
> |20|HR|
> 
> Both datasets are sorted by `dept_id`.
> 
> Hive can scan the sorted data and match keys as it proceeds.
> 
> ### How does the merge work?
> 
> Imagine two pointers moving through the sorted records.
> 
> ```
> Employees                       Departments
>     |                                |
>     v                                v
>  dept_id = 10                    dept_id = 10
>     |                                |
>     └────────── MATCH: IT ───────────┘
>                     |
>                     v
>               Output: Amit, IT
>               Output: Ravi, IT
> ```
> 
> When the keys match, Hive produces the joined records. When a key is smaller on one side, the scan advances on that side until matching keys are found.
> 
> ### Where do buckets help?
> 
> Suppose both tables have compatible bucket layouts based on `dept_id`.
> 
> ```
> Employees                       Departments
>     |                                |
>     v                                v
>   Bucket 0                         Bucket 0
>   Bucket 1                         Bucket 1
>   Bucket 2                         Bucket 2
>   Bucket 3                         Bucket 3
> ```
> 
> With compatible layouts, Hive can join corresponding buckets instead of requiring a full shuffle to bring all matching records together.
> 
> **Important:** SMB joins require more than simply having the same number of buckets. The bucketing columns, sorting order, and other compatibility requirements must be satisfied, and Hive must choose an execution plan that uses the SMB strategy.
> 
> ### Advantages
> 
> - Can avoid a full shuffle when the required layouts are compatible.
> - Can be useful for joining large tables.
> - Sorted data allows efficient merging of matching keys.
> 
> ### Limitations
> 
> - Requires appropriate bucketed and sorted data.
> - Maintaining those layouts adds work during data preparation and loading.
> 
> **Remember:** SMB Join = Use compatible buckets and sorted records to merge matching keys efficiently.
> 
> ---
> 
> # 5. Final Comparison — Exam Revision
> 
> |Feature|Shuffle Join|Map (Broadcast) Join|SMB Join|
> |---|---|---|---|
> |Main idea|Shuffle matching keys to reducers|Make small table available to mappers|Merge compatible, sorted bucket data|
> |Best suited for|Large tables when shuffle-based joining is appropriate|One small table and one large table|Large tables with suitable bucketed and sorted layouts|
> |Usual join shuffle|Required|Avoided for the join|Can be avoided when layouts are compatible|
> |Requires a small table?|No|Yes, typically|No|
> |Requires bucketed tables?|No|No|Yes|
> |Requires sorted data?|Shuffle typically sorts/groups keys|Not necessarily|Yes|
> |Main concern|Network shuffle cost|Memory needed for small table|Maintaining compatible layouts|
>

> 
> ```

> These three names describe **different execution strategies**, not three different SQL join types.

> # 19. Hive Join Strategies
> 
> In Part 1, you learned how to join two tables using SQL:
> 
> ```
> SELECT *
> FROM customer
> JOIN orders
> ON customer.id = orders.cid;
> ```
> 
> But there's another important question:
> 
> **How does Hive actually perform the join when the tables contain millions of records?**
> 
> Different join strategies determine how the data is moved, organized, and matched across the cluster.
> 
> Your PDF introduces three strategies:
> 
> 1. Shuffle Join
> 2. Map Join (Broadcast Join)
> 3. Sort-Merge-Bucket (SMB) Join
> 
> The correct strategy depends on table sizes, data organization, and the resources available.
> 
> ## 19.1 Shuffle Join (Reduce-Side Join)
> 
> A **Shuffle Join** brings records with matching join keys together so that they can be joined during the reduce phase of a MapReduce-style execution.
> 
> It is a general-purpose strategy that can work even when both tables are large.
> 
> ### Example
> 
> Suppose we have two tables.
> 
> **Customer table**
> 
> |id|first|last|
> |---|---|---|
> |11911|Nick|Toner|
> |11912|Jessie|Simonds|
> |11914|Rodger|Clayton|
> 
> **Orders table**
> 
> |cid|price|quantity|
> |---|---|---|
> |11914|12.25|27|
> |11914|40.50|10|
> |11911|10.50|3|
> 
> The join condition is:
> 
> ```
> SELECT *
> FROM customer
> JOIN orders
> ON customer.id = orders.cid;
> ```
> 
> Notice that `customer.id` matches `orders.cid`.
> 
> ### How Shuffle Join works
> 
> ```
>          CUSTOMER TABLE                ORDERS TABLE
>                 |                            |
>                 v                            v
>              Mapper                       Mapper
>                 |                            |
>                 v                            v
>        Emit join key = id          Emit join key = cid
>                 |                            |
>                 +-------------+--------------+
>                               |
>                               v
>                        SHUFFLE PHASE
>                   Group records by join key
>                               |
>                               v
>                         REDUCE PHASE
>                    Match records with the
>                      same join key
>                               |
>                               v
>                        JOINED OUTPUT
> ```
> 
> For example, all records with join key `11914` are sent to the same reducer, which matches the customer record with the corresponding order records.
> 
> The result includes:
> 0
> |customer.id|first|last|orders.cid|price|quantity|
> |---|---|---|---|---|---|
> |11914|Rodger|Clayton|11914|12.25|27|
> |11914|Rodger|Clayton|11914|40.50|10|
> 
> The customer record appears twice because two orders match that customer.
> 
> ### Why is it called a Shuffle Join?
> 
> The join keys and their associated records are redistributed across the cluster during the **shuffle phase**.
> 
> This allows records from different input datasets to meet at the same reducer.
> 
> ### Advantages
> 
> - Works with large tables.
> - Does not require the entire smaller table to fit in mapper memory.
> - Does not require both tables to have a prearranged bucket layout.
> 
> ### Disadvantage
> 
> - Shuffling large amounts of data over the network can be expensive.
> - It can require significant disk and network I/O.
> 
> **Remember:** Shuffle Join = redistribute records by join key, then join them on the reduce side.
> 
> ---
> 
> ## 19.2 Map Join (Broadcast Join)
> 
> A **Map Join** is useful when one table is small enough to fit into memory and the other table is large.
> 
> Instead of shuffling both datasets and joining records on the reduce side, Hive makes the small table available to the mapper tasks. Each mapper scans its portion of the large table and performs the join locally.
> 
> This is also called a **Broadcast Join** because the small table is distributed to the workers processing the large table.
> 
> ### Example
> 
> Suppose:
> 
> - `customer` contains a few thousand records.
> - `orders` contains hundreds of millions of records.
> 
> We want to join them using `customer.id = orders.cid`.
> 
> ### How Map Join works
> 
> ```
>         SMALL TABLE                    LARGE TABLE
>          customer                        orders
>              |                              |
>              v                              v
>        Distribute the                Split into input
>        small table to                portions for mappers
>        mapper tasks                         |
>              |                              |
>              v                              v
>        +-------------+               +-------------+
>        |   Mapper 1  |               |   Mapper 1  |
>        | Small table |<--------------| Orders data |
>        | in memory   |               +-------------+
>        +-------------+
>              |
>              v
>        +-------------+               +-------------+
>        |   Mapper 2  |               |   Mapper 2  |
>        | Small table |<--------------| Orders data |
>        | in memory   |               +-------------+
>        +-------------+
>              |
>              v
>         Joined output
> ```
> 
> Conceptually, every mapper has access to the small table, so it can match the large table's records without shuffling both datasets to reducers.
> 
> ### Why is Map Join faster?
> 
> A large table can be scanned once while each mapper performs the join locally.
> 
> This avoids the expensive shuffle required by a conventional reduce-side join.
> 
> ### Advantages
> 
> - Often much faster than a shuffle join.
> - Avoids shuffling both tables for the join.
> - Particularly useful when joining a large fact table with a small dimension table.
> 
> ### Disadvantage
> 
> - The small table must fit within the available memory resources of the workers performing the join.
> - Broadcasting a table that is too large can cause memory pressure or task failures.
> 
> **Remember:** Map Join = small table distributed to mappers + local join against the large table.
> 
> ---
> 
> ## 19.3 Sort-Merge-Bucket (SMB) Join
> 
> An **SMB Join** takes advantage of tables that have already been organized into buckets and sorted by their join keys.
> 
> Unlike a broadcast join, it can be useful when both tables are large.
> 
> ### First, connect it to bucketing
> 
> In Part 1, you learned that bucketing divides records into a fixed number of groups based on a hash of a specified column.
> 
> For example:
> 
> ```
> CREATE TABLE orders (
>     cid INT,
>     price FLOAT,
>     quantity INT
> )
> CLUSTERED BY (cid)
> SORTED BY (cid)
> INTO 32 BUCKETS;
> ```
> 
> This defines a table bucketed by `cid` and sorted by `cid` within its buckets.
> 
> A corresponding customer table could be defined as:
> 
> ```
> CREATE TABLE customer (
>     id INT,
>     first STRING,
>     last STRING
> )
> CLUSTERED BY (id)
> SORTED BY (id)
> INTO 32 BUCKETS;
> ```
> 
> The example illustrates the intended layout. For an SMB join to be eligible, the actual tables must satisfy Hive's requirements for bucket counts, bucket-column compatibility, sorting, and other relevant settings. Simply declaring these properties does not guarantee that existing data is physically organized correctly.
> 
> ### How SMB Join works
> 
> ```
>         CUSTOMER TABLE                 ORDERS TABLE
>         Bucketed by id                 Bucketed by cid
>         Sorted by id                   Sorted by cid
>                |                              |
>                v                              v
>          Corresponding                 Corresponding
>          bucket files                  bucket files
>                |                              |
>                +--------------+---------------+
>                               |
>                               v
>                      SORT-MERGE JOIN
>                               |
>                  Read sorted records together
>                  and match equal join keys
>                               |
>                               v
>                          JOINED OUTPUT
> ```
> 
> Because the data is already organized appropriately, Hive can take advantage of that layout to perform an efficient join without necessarily redistributing all the records through a conventional shuffle join.
> 
> ### Advantages
> 
> - Can be efficient for large tables.
> - Can reduce the need for expensive data redistribution.
> - Makes use of pre-existing sorted and bucketed data.
> 
> ### Disadvantages
> 
> - The data must be organized appropriately in advance.
> - Creating and maintaining that layout requires additional work.
> - The join is only eligible when the tables and query satisfy the necessary conditions.
> 
> **Remember:** SMB Join = compatible bucketed tables + sorted join keys + merge-based joining.
> 
> ---
> 
> ## 19.4 Compare all three join strategies
> 
> The first page of your PDF summarizes their approaches, advantages, and limitations.
> 
> |Feature|Shuffle Join|Map (Broadcast) Join|Sort-Merge-Bucket Join|
> |---|---|---|---|
> |Main approach|Redistribute join keys and join on the reduce side|Load the small table into memory and join during mapping|Take advantage of compatible sorted and bucketed data|
> |Best suited for|Large tables without a special layout requirement|One small table and one large table|Large tables with suitable pre-existing layouts|
> |Data shuffle|Usually requires shuffle of join data|Avoids the conventional shuffle of both tables|Can avoid conventional shuffle when the layout is suitable|
> |Memory requirement|Does not require the entire small table in mapper memory|Small table must fit within available memory|Depends on execution and join implementation|
> |Main advantage|General-purpose|Often very fast for a large–small join|Efficient for suitably organized tables|
> |Main limitation|Network and disk overhead|Small table must be sufficiently small|Requires suitable sorting and bucketing|
> 
> ### Which join should you choose?
> 
> ```
>               Need to join two tables
>                         |
>              +----------+----------+
>              |                     |
>              v                     v
>       Is one table small?    Both tables are large?
>              |                     |
>         +----+----+                |
>         |         |                v
>        Yes        No        Are they already suitably
>         |                   bucketed and sorted?
>         v                          |
>     Map Join                  +----+----+
>                               |         |
>                              Yes        No
>                               |         |
>                               v         v
>                          SMB Join   Shuffle Join
> ```
> 
> This is a useful initial decision guide, not an absolute rule. Hive's optimizer chooses or transforms join plans based on the query, statistics, configuration, and execution engine.
> 
> ### Important connection to MapReduce
> 
> - **Shuffle Join:** records are brought together by key before joining.
> - **Map Join:** the join can be performed during the map phase using a small in-memory table.
> - **SMB Join:** the existing sorted and bucketed layout helps the join.
> 
> These are **join strategies**, not three different SQL join types. For example, an inner join describes which matching rows to return, while a shuffle or broadcast join describes how the work is performed.

> ## 20.1 What is a UDF?
> 
> A **UDF (User-Defined Function)** is a custom function that adds functionality to HiveQL.

> 
> ```

> ```

>                            |

> ## 20.2 Types of user-defined functions
> 
> Hive supports several kinds of custom functions.

> |---|---|

>

> ## 20.3 Invoking a Hive UDF

> 
> ```
> ADD JAR /myapp/lib/myhiveudfs.jar;
> ```

> ### Step 2: Register the function

> - `ComputeShipping` is the function name to use in queries.
> - `hiveudfs.ComputeShipping` identifies the Java class implementing the function.

>

>      |

> 
> The PDF contains a lab titled **Writing a Hive UDF**, but it does not include the full implementation in the extracted slides.

> 
> 1. Creating a Java class.
> 2. Extending the appropriate Hive UDF base class.

> # 21. Computing N-grams in Hive
> 
> In Part 1, we introduced n-grams as sequences of consecutive words. Your second PDF now shows how Hive can compute them using built-in functions.
> 
> This is an important example because it demonstrates that Hive can do more than ordinary filtering, grouping, and joining: it can also support text analysis.
> 
> ## 21.1 Understanding the input
> 
> Suppose a Hive table named `mytable` contains a column called `val` with text:
> 
> ```
> I liked the big data course
> I liked the Hadoop course
> I liked the Python course
> ```
> 
> Our objective is to discover commonly occurring sequences of words.
> 
> ### Types of n-grams
> 
> For the sentence:
> 
> ```
> I liked the big data course
> ```
> 
> |Type|N-gram examples|
> |---|---|
> |Unigram (n = 1)|`I`, `liked`, `the`, `big`|
> |Bigram (n = 2)|`I liked`, `liked the`, `the big`|
> |Trigram (n = 3)|`I liked the`, `liked the big`, `the big data`|
> 
> **An n-gram is a sequence of `n` consecutive words or other tokens.**
> 
> ## 21.2 Understanding `sentences()`
> 
> The PDF uses the function:
> 
> ```
> sentences(val)
> ```
> 
> This function converts a text value into a nested representation of sentences and words, which can then be processed by Hive's n-gram functions.
> 
> Conceptually:
> 
> ```
> Text column: val
>        |
>        v
> sentences(val)
>        |
>        v
> Sentence/word representation
>        |
>        v
> N-gram processing
> ```
> 
> This is useful because the n-gram functions need to work with words and sentence boundaries, not simply an unstructured string.
> 
> ## 21.3 The `ngrams()` function
> 
> The PDF gives this query:
> 
> ```
> SELECT ngrams(sentences(val), 2, 100)
> FROM mytable;
> ```
> 
> The function is called with three arguments:
> 
> ```
> ngrams(sentences, N, K)
> ```
> 
> - **`sentences`**: the sentence-and-word representation to analyse.
> - **`N = 2`**: generate bigrams, meaning sequences of two consecutive words.
> - **`K = 100`**: return up to 100 of the most frequent n-grams.
> 
> The function aggregates n-gram frequencies over the supplied input for the query.
> 
> For example, across the sample sentences, `I liked` occurs three times.
> 
> The function can return common sequences with their associated frequencies, rather than requiring you to implement all the counting logic manually.
> 
> ### What happens in the query?
> 
> ```
> mytable
>    |
>    v
> sentences(val)
>    |
>    v
> Split text into sentence/word structure
>    |
>    v
> ngrams(..., 2, 100)
>    |
>    v
> Find frequent two-word sequences
> ```
> 
> **Remember:** `ngrams(sentences(val), 2, 100)` computes frequent bigrams from the text.

> ## 21.4 The `context_ngrams()` function
> 
> The PDF also provides:

> ```

> ```
> 
> The array contains:
> 
> - `"error"`: a known word.
> - `"code"`: another known word.

> 
> Conceptually, this asks Hive to find frequent three-word sequences matching the pattern:
> 
> ```

> ```
>

> 
> ```

> 
> ```

> error code failed

> ```

> 
> The exact output depends on the input text and the function's context-matching behaviour.

> ### Compare `ngrams()` and `context_ngrams()`
> 
> |Feature|`ngrams()`|`context_ngrams()`|

> # Avro in Hadoop / Hive
> 
> Avro is a data serialization framework used to store and exchange structured data efficiently in the Hadoop ecosystem.
> 
> In simple words, Avro provides a way to convert structured data into a compact binary format so that it can be stored, transferred, and processed by different applications.
> 
> Let's understand why it is needed and how it fits into Hive.
> 
> ## 1. Why do we need Avro?
> 
> Suppose you have an email record:
> 
> ```
> Name: Rahul
> Email: rahul@gmail.com
> Age: 25
> ```
> 
> You could store it in a text file like CSV:
> 
> ```
> Rahul,rahul@gmail.com,25
> ```
> 
> But there are some limitations with plain text formats:
> 
> - The structure and data types are not always explicitly defined.
>     
> - Applications need to know how to interpret each field.
>     
> - Changes to the data structure can cause compatibility problems.
>     
> 
> Avro addresses these problems using a schema.
> 
> ## 2. What is an Avro schema?
> 
> A schema defines the structure of your data: field names, data types, and other details.
> 
> For example:
> 
> ```
> {
>   "type": "record",
>   "name": "Student",
>   "fields": [
>     {"name": "name", "type": "string"},
>     {"name": "email", "type": "string"},
>     {"name": "age", "type": "int"}
>   ]
> }
> ```
> 
> This schema tells Avro:
> 
> |Field|Data type|
> |---|---|
> |name|string|
> |email|string|
> |age|int|
> 
> So, when Avro reads or writes a record, it knows how to interpret each field.
> 
> ## 3. How does Avro store data?
> 
> Avro mainly stores data in a binary format, rather than storing everything as readable text.
> 
> For example, consider these two representations:
> 
> JSON representation (readable)
> 
> ```
> {"name":"Rahul","email":"rahul@gmail.com","age":25}
> ```
> 
> Avro representation (binary)
> 
> The record is encoded into bytes according to its schema. It is not directly human-readable like JSON.
> 
> An Avro Object Container File (commonly `.avro`) generally contains:
> 
> 1. Header: Includes the schema and file metadata.
>     
> 2. Data blocks: Contains serialized records.
>     
> 3. Sync markers: Help identify block boundaries and support splitting files for distributed processing.
>     
> 
> So, an Avro file carries the schema along with the serialized data. The reader can use that schema to interpret the records.
> 
> ## 4. Important features of Avro
> 
> 4. Schema-based
> 
> - Every record follows a defined schema.
>     
> - Schema specifies field names and data types.
>     
> - Helps applications understand the structure of data.
>     
> 
> 2. Compact binary format
> 
> - Stores data in binary representation.
>     
> - Generally more compact than equivalent plain-text JSON.
>     
> - Reduces storage and data transfer overhead.
>     
> 
> 3. Schema evolution
> 
> This is one of Avro's most important features.
> 
> Suppose your original schema is:
> 
> ```
> Student:
>     name: string
>     age: int
> ```
> 
> Later, your application needs an additional field:
> 
> ```
> Student:
>     name: string
>     age: int
>     city: string
> ```
> 
> Avro supports controlled schema changes while maintaining compatibility, provided the changes follow its schema-resolution rules.
> 
> For example, a new field can have a default value so older records can still be read using the new schema.
> 
> 4. Language interoperability
> 
> - Supports multiple programming languages.
>     
> - Data written by one application can be read by another application that understands the schema.
>     
> 
> ## 5. How does Avro fit into Hadoop and Hive?
> 
> Imagine you have a large collection of emails stored in Avro format.
> 
> ```
> Email data
>     |
>     v
> Avro files (.avro)
>     |
>     v
> HDFS (distributed storage)
>     |
>     v
> Hive reads Avro records using their schema
>     |
>     v
> HiveQL queries / analysis
>     |
>     v
> N-gram analysis, filtering, aggregation, etc.
> ```
> 
> Avro acts as the data storage and serialization format. Hive acts as the query and processing layer.
> 
> For example, Hive can define a table using Avro:
> 
> ```
> CREATE TABLE emails (
>     id INT,
>     sender STRING,
>     val STRING
> )
> STORED AS AVRO;
> ```
> 
> Hive needs access to the appropriate Avro schema to interpret the records. In practice, this can be provided through table properties such as `avro.schema.url` or an inline schema.
> 
> ## 6. Avro vs CSV vs Parquet
> 
> |Feature|CSV|Avro|Parquet|
> |---|---|---|---|
> |Format|Text|Binary|Binary|
> |Schema|Not inherently defined|Yes|Yes|
> |Storage style|Row-like text records|Row-based|Columnar|
> |Schema evolution|Limited|Supported|Supported|
> |Best suited for|Simple data exchange|Data serialization and record exchange|Analytical queries|
> 
> Remember this distinction:
> 
> - Avro: Row-based format, useful for serialization and data exchange.
>     
> - Parquet: Columnar format, useful for analytical queries that read selected columns.
>     
> - CSV: Simple text format, easy for humans to read.
>     
> 
> ## One-glance revision
> 
> ```
> AVRO
>  |
>  +-- Data serialization framework
>  |
>  +-- Stores structured data in binary format
>  |
>  +-- Uses SCHEMA
>  |      |
>  |      +-- Field names
>  |      +-- Data types
>  |      +-- Structure of records
>  |
>  +-- Important features
>  |      |
>  |      +-- Compact binary storage
>  |      +-- Schema evolution
>  |      +-- Language interoperability
>  |
>  +-- Hadoop integration
>         |
>         +-- Stores .avro files in HDFS
>         +-- Hive reads and processes Avro data
>         +-- Useful for processing structured datasets
> ```
> 
> The main concept to remember: Avro is not a query engine like Hive or a storage system like HDFS. It is a format and serialization framework that defines how structured data is represented, stored, and interpreted.

> # 1. Multi-Table / File Insert
> 
> ### Concept
> 
> Normally, we may execute separate queries to send results to different tables or directories. Hive supports **multi-table inserts**, allowing multiple outputs to be produced from the same source query.
> 
> This can avoid repeatedly reading the same source data.
> 
> ### Example 1: Write results to different HDFS directories
> 
> ```
> FROM wh_visits
> INSERT OVERWRITE DIRECTORY '2014_visitors'
> SELECT *
> WHERE visit_year = '2014'
> 
> INSERT OVERWRITE DIRECTORY 'ca_congress'
> SELECT *
> WHERE state = 'CA';
> ```
> 
> **Meaning:**
> 
> - First output: visitors from 2014.
>     
> - Second output: records matching the condition `state = 'CA'`.
>     
> - `INSERT OVERWRITE DIRECTORY`: writes the result to a directory, replacing its existing contents according to Hive's overwrite behavior.
>     
> 
> **Important:** In this multi-insert syntax, do not put a semicolon after the first `SELECT`; it terminates the statement. Put the semicolon at the end.
> 
> ### Example 2: Write to a table and a directory
> 
> ```
> FROM visitors
> INSERT OVERWRITE TABLE gender_sum
> SELECT gender, COUNT(DISTINCT userid)
> GROUP BY gender
> 
> INSERT OVERWRITE DIRECTORY '/user/tmp/age_sum'
> SELECT age, COUNT(DISTINCT userid)
> GROUP BY age;
> ```
> 
> Here, the same source table produces:
> 
> - Gender-wise distinct user counts in `gender_sum`.
>     
> - Age-wise distinct user counts in the specified directory.
>     
> 
> **Remember:** One source → multiple outputs.

> # 2. Hive Views
> 
> ## 2.1 What is a View?
> 
> A **view is a virtual table defined by a query**.
> 
> Unlike a normal Hive table, a standard view does not store its own result data. Instead, Hive stores the view definition in the Metastore and evaluates its query when the view is used.
> 
> Connect this to our earlier Hive notes:
> 
> - **Table:** Metadata in the Metastore; data is stored in HDFS or another configured storage location.
>     
> - **View:** Query definition in the Metastore; no separate underlying result dataset is normally stored.
>     
> 
> ### Why use views?
> 
> - Simplify complex queries.
>     
> - Reuse frequently needed query logic.
>     
> - Present selected columns or filtered records.
>     
> - Hide unnecessary columns from users of the view.
>     
> 
> ## 2.2 Creating a View
> 
> Suppose `wh_visits` contains visitor records, including arrival time.
> 
> We want a view containing visitors from 2010.
> 
> ```
> CREATE VIEW visitors_2010 AS
> SELECT
>     fname,
>     lname,
>     time_of_arrival,
>     info_comment
> FROM wh_visits
> WHERE CAST(SUBSTRING(time_of_arrival, 6, 4) AS INT) >= 2010
>   AND CAST(SUBSTRING(time_of_arrival, 6, 4) AS INT) < 2011;
> ```
> 
> The expression extracts the year from the expected date string format, converts it to an integer, and filters for 2010.
> 
> **Conceptual flow:**
> 
> ```
> wh_visits table
>       |
>       v
> Apply the query and year filter
>       |
>       v
> Define visitors_2010 view
>       |
>       v
> Query the view whenever required
> ```
> 
> The view definition is stored, not a separate copy of all the matching records.
> 
> ## 2.3 Using a View
> 
> A view can be queried much like a table.
> 
> ```
> SELECT *
> FROM visitors_2010
> WHERE info_comment LIKE '%CONGRESS%'
> ORDER BY lname;
> ```
> 
> This query:
> 
> 1. Uses the view's underlying query.
>     
> 2. Filters records whose comments contain `CONGRESS`.
>     
> 3. Orders the result by last name.
>     
> 
> **Key point:** A view is a reusable query, not necessarily a stored dataset.
>

> # 3. The `OVER` Clause
> 
> This is one of the most important concepts in advanced Hive analytics.
> 
> ## 3.1 The Problem with `GROUP BY`
> 
> Suppose an `orders` table contains:
> 
> |cid|price|quantity|
> |---|---|---|
> |4150|10.50|3|
> |11914|12.25|27|
> |4150|5.99|5|
> |2934|39.99|22|
> |11914|40.50|10|
> 
> Here, `cid` identifies a customer.
> 
> Suppose we want the maximum purchase price for each customer.
> 
> ### Using `GROUP BY`
> 
> ```
> SELECT cid, MAX(price)
> FROM orders
> GROUP BY cid;
> ```
> 
> This produces one row per customer.
> 
> |cid|max(price)|
> |---|---|
> |4150|10.50|
> |11914|40.50|
> |2934|39.99|
> 
> **Problem:** The individual order rows are no longer present in the result.
> 
> ### Using `OVER (PARTITION BY ...)`
> 
> ```
> SELECT
>     cid,
>     MAX(price) OVER (PARTITION BY cid) AS max_price
> FROM orders;
> ```
> 
> Now the result retains every input row and adds the maximum price for that customer's group.
> 
> |cid|max_price|
> |---|---|
> |4150|10.50|
> |11914|40.50|
> |4150|10.50|
> |2934|39.99|
> |11914|40.50|
> 
> ### The main difference
> 
> - `GROUP BY` combines rows into groups and usually produces one result row per group.
>     
> - `OVER (PARTITION BY ...)` calculates a value for each group but preserves the individual rows.
>     
> 
> This is the basic idea of a **window function**.
> 
> ## 3.2 Understanding `PARTITION BY`
> 
> ```
> MAX(price) OVER (PARTITION BY cid)
> ```
> 
> Think of it as:
> 
> ```
> All orders
>     |
>     v
> Divide logically by cid
>     |
>     +---- cid 4150 ----> Find maximum price
>     |
>     +---- cid 11914 ---> Find maximum price
>     |
>     +---- cid 2934 ----> Find maximum price
>     |
>     v
> Attach each customer's maximum to their original rows
> ```
> 
> Here, `PARTITION BY` defines the groups over which the calculation operates. It does not itself remove rows from the output.
> 
> **Important:** This is a logical grouping for analytics, not the same thing as creating physical Hive table partitions.
> 
> ---
> 
> # 4. Window Frames
> 
> The `OVER` clause can do more than calculate a value across an entire partition.
> 
> A **window frame** specifies which rows around the current row should be included in the calculation.
> 
> ### General syntax
> 
> ```
> FUNCTION(column) OVER (
>     PARTITION BY column
>     ORDER BY column
>     ROWS BETWEEN start AND end
> )
> ```
> 
> - `PARTITION BY`: Divides rows into groups.
>     
> - `ORDER BY`: Establishes the order within each group.
>     
> - `ROWS BETWEEN`: Specifies the rows included in the current calculation.
>     
> 
> ## 4.1 Example: Two preceding rows through the current row
> 
> ```
> SELECT
>     cid,
>     price,
>     SUM(price) OVER (
>         PARTITION BY cid
>         ORDER BY price
>         ROWS BETWEEN 2 PRECEDING AND CURRENT ROW
>     ) AS running_sum
> FROM orders;
> ```
> 
> For each row, Hive sums:
> 
> - The current row.
>     
> - Up to two preceding rows in the specified order.
>     
> - Only rows belonging to the same `cid` partition.
>     
> 
> For customer `4150`, suppose prices in ascending order are:
> 
> |Price|Calculation|Sum|
> |---|---|---|
> |5.99|5.99|5.99|
> |10.50|5.99 + 10.50|16.49|
> |20.00|5.99 + 10.50 + 20.00|36.49|
> |39.99|10.50 + 20.00 + 39.99|70.49|
> 
> The window moves as Hive processes each row.
> 
> Notice that the fourth row includes only the current row and the two immediately preceding rows, not every previous row.
> 
> ## 4.2 Other window-frame expressions
> 
> ### A. Include two preceding and three following rows
> 
> ```
> SUM(price) OVER (
>     PARTITION BY cid
>     ORDER BY price
>     ROWS BETWEEN 2 PRECEDING AND 3 FOLLOWING
> )
> ```
> 
> The frame includes:
> 
> - Up to two rows before the current row.
>     
> - The current row.
>     
> - Up to three rows after it.
>     
> 
> ### B. Running total from the beginning
> 
> ```
> SUM(price) OVER (
>     PARTITION BY cid
>     ORDER BY price
>     ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW
> )
> ```
> 
> `UNBOUNDED PRECEDING` means the frame begins at the first row of the current partition.
> 
> The calculation includes every row from that starting point through the current row.
> 
> ```
> Row 1: A
> Row 2: A + B
> Row 3: A + B + C
> Row 4: A + B + C + D
> ```
> 
> This is useful for running totals and cumulative calculations.
> 
> **Revision tip:**
> 
> |Expression|Meaning|
> |---|---|
> |`CURRENT ROW`|The current row|
> |`1 PRECEDING`|One row before|
> |`2 PRECEDING`|Two rows before|
> |`3 FOLLOWING`|Three rows after|
> |`UNBOUNDED PRECEDING`|From the beginning of the partition|
> |`UNBOUNDED FOLLOWING`|Through the end of the partition|
> 
> The precise frame boundaries depend on the specified start and end, as well as how many rows exist near the boundaries.
>

> # 5. Hive Analytic Functions
> 
> Hive supports analytical functions that calculate rankings and other values across rows.
> 
> The PDF demonstrates the `RANK()` function.
> 
> ## Example: Rank orders by quantity for each customer
> 
> ```
> SELECT
>     cid,
>     quantity,
>     RANK() OVER (
>         PARTITION BY cid
>         ORDER BY quantity
>     ) AS order_rank
> FROM orders;
> ```
> 
> ### How it works
> 
> 1. `PARTITION BY cid`: Separates customers.
>     
> 2. `ORDER BY quantity`: Orders each customer's records by quantity.
>     
> 3. `RANK()`: Assigns ranks within each customer group.
>     
> 
> For example:
> 
> |cid|quantity|rank|
> |---|---|---|
> |4150|2|1|
> |4150|3|2|
> |4150|5|3|
> |4150|22|4|
> |11914|10|1|
> |11914|27|2|
> 
> Each customer's ranking starts again from 1.
> 
> ### Important distinction
> 
> `RANK()` assigns the same rank to tied values and leaves gaps after ties.
> 
> For example, if the ordered values are `10, 20, 20, 30`, their ranks are `1, 2, 2, 4`.
> 
> Other common ranking functions include:
> 
> - `ROW_NUMBER()`: Assigns a distinct sequential number to each row.
>     
> - `RANK()`: Allows ties and leaves gaps.
>     
> - `DENSE_RANK()`: Allows ties without leaving gaps.
>     
> 
> **Use case:** Ranking customers' purchases, employees' salaries, products' sales, and other grouped data.
>

> # 6. Hive File Formats
> 
> So far, we have focused on how Hive organizes and processes data. Now let's look at how that data is physically stored.
> 
> Your PDF lists four formats:
> 
> 1. Text file
>     
> 2. SequenceFile
>     
> 3. RCFile
>     
> 4. ORC File
>     
> 
> ## 6.1 Text File
> 
> - Stores data in a human-readable text representation.
>     
> - Commonly uses delimiters such as commas or tabs.
>     
> - Simple to inspect and exchange.
>     
> - Parsing text can require more work during processing.
>     
> 
> ## 6.2 SequenceFile
> 
> - A Hadoop binary file format.
>     
> - Stores data as key-value records.
>     
> - Supports binary data rather than requiring everything to be plain text.
>     
> 
> ## 6.3 RCFile
> 
> **RCFile = Record Columnar File.**
> 
> - Combines ideas from row-based and column-based storage.
>     
> - Organizes records into row groups and stores column data within those groups.
>     
> - Was designed to improve data processing efficiency in Hive.
>     
> 
> Example from the PDF:
> 
> ```
> CREATE TABLE names (
>     fname STRING,
>     lname STRING
> )
> STORED AS RCFILE;
> ```
> 
> ## 6.4 ORC File
> 
> **ORC = Optimized Row Columnar.**
> 
> ORC is a columnar storage format designed to store Hive data efficiently.
> 
> Its columnar layout can help queries that read only selected columns, while compression and encoding can reduce storage and I/O costs.
> 
> Example:
> 
> ```
> CREATE TABLE students (
>     id INT,
>     name STRING,
>     age INT
> )
> STORED AS ORC;
> ```
> 
> You can also change a table's file format:
> 
> ```
> ALTER TABLE tablename SET FILEFORMAT ORC;
> ```
> 
> To set ORC as the default file format for a Hive session:
> 
> ```
> SET hive.default.fileformat=Orc;
> ```
> 
> ### Why is ORC important?
> 
> Suppose a table has 50 columns, but a query needs only `name` and `age`.
> 
> With a suitable columnar format, Hive can often read only the required columns rather than reading all 50 columns.
> 
> This can reduce unnecessary disk I/O.
> 
> ### Quick comparison
> 
> |Format|Storage style|Main point|
> |---|---|---|
> |Text file|Text-based|Simple and readable|
> |SequenceFile|Binary key-value|Hadoop binary storage|
> |RCFile|Hybrid row/column organization|Earlier column-oriented Hive format|
> |ORC|Columnar|Efficient storage and analytical processing|
> 
> **Connection to previous notes:** Avro is another schema-based format, primarily row-oriented. ORC is particularly useful for Hive analytical workloads.
>

> # 7. Hive SerDe
> 
> This topic connects file formats to how Hive interprets data.
> 
> ## 7.1 What is SerDe?
> 
> **SerDe = Serializer/Deserializer.**
> 
> It determines how Hive converts between stored data and the records or objects Hive processes.
> 
> - **Deserializer:** Converts stored data into a representation Hive can process.
>     
> - **Serializer:** Converts Hive's records into a representation suitable for storage.
>     
> 
> Think of it as a translator between Hive and the underlying file representation.
> 
> ```
> Reading data:
> 
> HDFS file
>     |
>     v
> Deserializer
>     |
>     v
> Hive records
> 
> 
> Writing data:
> 
> Hive records
>     |
>     v
> Serializer
>     |
>     v
> HDFS file
> ```
> 
> ## 7.2 Why do we need SerDe?
> 
> Different formats store data differently.
> 
> For example:
> 
> - A delimited text file stores values as text separated by delimiters.
>     
> - Avro stores serialized records according to a schema.
>     
> - ORC stores data in a columnar representation.
>     
> 
> Hive needs the appropriate mechanisms to interpret the format.
> 
> ## 7.3 Avro SerDe example from the PDF
> 
> ```
> CREATE TABLE emails (
>     from_field STRING,
>     sender STRING,
>     email_body STRING
> )
> ROW FORMAT SERDE
> 'org.apache.hadoop.hive.serde2.avro.AvroSerDe'
> STORED AS INPUTFORMAT
> 'org.apache.hadoop.hive.ql.io.avro.AvroContainerInputFormat'
> OUTPUTFORMAT
> 'org.apache.hadoop.hive.ql.io.avro.AvroContainerOutputFormat'
> TBLPROPERTIES (
>     'avro.schema.url'='hdfs://nn:8020/emailschema.avsc'
> );
> ```
> 
> _The PDF's displayed URL appears to omit a colon after_ `_hdfs_`_; the example above uses the conventional_ `_hdfs://_` _form._
> 
> Understanding the components:
> 
> |Component|Purpose|
> |---|---|
> |Column definitions|Describe the fields exposed by the Hive table|
> |`ROW FORMAT SERDE`|Specifies the Avro SerDe|
> |`INPUTFORMAT`|Specifies how input files are read|
> |`OUTPUTFORMAT`|Specifies how output files are written|
> |`avro.schema.url`|Points to the Avro schema file|
> 
> Here, `emailschema.avsc` supplies the schema used to interpret Avro records.
> 
> **Important:** Avro is the data format; Avro SerDe is the mechanism Hive uses to interpret the records.

> # 8. Computing Table and Column Statistics
> 
> Hive can collect statistics about tables and columns to help understand the data and optimize queries.
> 
> Statistics may include information such as row counts, data sizes, and column characteristics.
> 
> ## 8.1 Compute table statistics
> 
> ```
> ANALYZE TABLE tablename COMPUTE STATISTICS;
> ```
> 
> Collects table-level statistics.
> 
> ## 8.2 Compute column statistics
> 
> ```
> ANALYZE TABLE tablename
> COMPUTE STATISTICS FOR COLUMNS column_name_1, column_name_2;
> ```
> 
> Collects statistics for the specified columns.
> 
> ## 8.3 Inspect table information
> 
> ```
> DESCRIBE FORMATTED tablename;
> ```
> 
> Displays detailed table metadata and properties.
> 
> ```
> DESCRIBE EXTENDED tablename;
> ```
> 
> Displays extended table information.
> 
> ### Why are statistics useful?
> 
> Imagine Hive must join two tables.
> 
> Without useful statistics, the optimizer may have limited information about their sizes and data distributions.
> 
> With statistics, it can make better-informed decisions about the query plan.
> 
> ```
> Table data
>     |
>     v
> ANALYZE TABLE
>     |
>     v
> Collect statistics
>     |
>     v
> Optimizer uses available statistics
>     |
>     v
> Choose a potentially more efficient query plan
> ```
> 
> **Remember:** `ANALYZE TABLE` collects statistics; it does not itself perform the query optimization.

> # 9. Hive Cost-Based Optimization (CBO)
> 
> ## 9.1 What is CBO?
> 
> **CBO = Cost-Based Optimization.**
> 
> CBO uses available information about data and estimated execution costs to choose an efficient query plan.
> 
> Your PDF identifies Apache Calcite as the open-source framework used by Hive's CBO.
> 
> ### Example
> 
> Suppose a query joins three tables.
> 
> There may be different ways to arrange the joins. Depending on table sizes, statistics, and other conditions, some execution plans may be more efficient than others.
> 
> The optimizer evaluates possible plans and chooses one based on its cost estimates.
> 
> ```
> HiveQL query
>      |
>      v
> Available table/column statistics
>      |
>      v
> Cost-Based Optimizer
>      |
>      v
> Choose an execution plan
>      |
>      v
> Execute the query
> ```
> 
> ## 9.2 Enabling CBO-related settings
> 
> The PDF gives the following examples:
> 
> ```
> ANALYZE TABLE tweets COMPUTE STATISTICS;
> 
> ANALYZE TABLE tweets
> COMPUTE STATISTICS FOR COLUMNS sender, topic;
> 
> SET hive.compute.query.using.stats=true;
> SET hive.cbo.enable=true;
> SET hive.stats.fetch.column.stats=true;
> ```
> 
> The first two statements collect statistics. The remaining statements configure statistics usage and cost-based optimization.
> 
> The exact properties available and their defaults can vary between Hive versions.
> 
> ### Key distinction
> 
> - **Statistics:** Information about the data.
>     
> - **CBO:** Uses available statistics and cost estimates to choose a query plan.
>     
> - **Query execution engine:** Executes the selected plan.
>     
> 
> CBO decides how a query should be executed; it is not itself the engine that executes the query.
>

> # 10. Vectorization
> 
> ## 10.1 What is vectorization?
> 
> Vectorization improves query processing by operating on a batch of rows at a time rather than processing each row individually through the same execution operations.
> 
> Conceptually:
> 
> **Without vectorization:**
> 
> ```
> Row 1 → Process
> Row 2 → Process
> Row 3 → Process
> Row 4 → Process
> ```
> 
> **With vectorization:**
> 
> ```
> Batch of rows
>       |
>       v
> Process a batch together
>       |
>       v
> Next batch
> ```
> 
> Batch-oriented processing can reduce per-row processing overhead and improve CPU efficiency.
> 
> ## 10.2 Vectorization + ORC
> 
> The PDF highlights the combination:
> 
> **Vectorization + ORC = major improvement in Hive query performance.**
> 
> Why?
> 
> - **ORC:** Helps reduce storage and data-reading costs through columnar storage and compression.
>     
> - **Vectorization:** Can reduce processing overhead by processing batches of rows.
>     
> 
> Together, they can improve performance for supported queries.
> 
> However, the benefit depends on the query, data format, Hive version, and whether the relevant operations support vectorization.
>

> # 12. Understanding Hive on Tez
> 
> This connects directly to our earlier MapReduce notes.
> 
> ## 12.1 The problem with a MapReduce execution plan
> 
> Suppose a Hive query performs two joins followed by aggregation:
> 
> ```
> SELECT
>     a.state,
>     COUNT(*),
>     AVG(c.price)
> FROM a
> JOIN b ON a.id = b.id
> JOIN c ON a.itemId = c.itemId
> GROUP BY a.state;
> ```
> 
> In a traditional multi-stage MapReduce execution plan, intermediate results may be written to HDFS between stages.
> 
> That can cause:
> 
> - Additional disk I/O.
>     
> - Extra job-stage overhead.
>     
> - Longer query execution time.
>     
> 
> ## 12.2 How Tez helps
> 
> **Apache Tez is a distributed data-processing framework that can execute Hive query plans as a directed acyclic graph (DAG) of processing tasks.**
> 
> Instead of requiring every stage to behave like a separate MapReduce job with intermediate results written to HDFS, Tez can connect stages and pass data between them more efficiently.
> 
> The PDF emphasizes that Tez avoids unnecessary HDFS writes.
> 
> ### Conceptual comparison
> 
> **Hive on MapReduce:**
> 
> ```
> Map → Reduce
>        |
>        v
>  Intermediate output in HDFS
>        |
>        v
> Map → Reduce
>        |
>        v
>  Intermediate output in HDFS
>        |
>        v
> Next stage
> ```
> 
> **Hive on Tez:**
> 
> ```
> Map → Reduce
>        |
>        v
> Next processing stage
>        |
>        v
> Further processing
> ```
> 
> This is a conceptual comparison. Actual execution plans can contain several parallel tasks and stages.
> 
> Tez can reduce unnecessary intermediate disk writes, but it does not eliminate every intermediate write or guarantee that every query will be faster.
> 
> ## 12.3 Configuring Tez
> 
> The PDF shows this setting:
> 
> ```
> SET hive.execution.engine=tez;
> ```
> 
> It can be configured in the Hive session or placed in the appropriate configuration file, such as `hive-site.xml`.
> 
> **Important distinction:**
> 
> - **CBO:** Helps choose an efficient query plan.
>     
> - **Tez:** Executes the plan using its processing framework.
>     
> - **MapReduce:** Another execution framework that Hive can use.
>     
>

> # 13. Hive Optimization Tips
> 
> The final slide of your PDF combines the practical recommendations from the earlier topics.
> 
> ## 13.1 Partition, bucket, and skew
> 
> Organize data so that Hive can avoid processing unnecessary records and distribute work effectively.
> 
> - **Partitioning:** Helps prune irrelevant partition directories when the query filters on partition columns.
>     
> - **Bucketing:** Organizes data into hash-based buckets, which can help with certain joins and processing patterns.
>     
> - **Skew handling:** Helps address uneven data distributions that can overload particular tasks.
>     
> 
> Remember our previous discussion: partitioning should use suitable columns, bucketing requires an appropriate design, and skew handling addresses disproportionate key frequencies.
> 
> ## 13.2 Use ORC
> 
> ORC provides columnar storage, compression, and other features that can improve analytical query performance.
> 
> ## 13.3 Sort and bucket on common join keys
> 
> Suitable sorting and bucketing arrangements can enable more efficient join strategies, including sort-merge-bucket joins when the necessary conditions are satisfied.
> 
> This connects directly to the join strategies in Part 2.
> 
> ## 13.4 Use map/broadcast joins when suitable
> 
> When one join input is sufficiently small, a map join can distribute that input to mapper tasks and avoid the conventional shuffle required by a reduce-side join.
> 
> Do not use this blindly: the smaller input must fit within the applicable memory constraints.
> 
> ## 13.5 Increase replication for hot data
> 
> The PDF recommends increasing the replication factor for hot data to reduce latency.
> 
> This can help when frequently accessed data benefits from additional replicas, but it also consumes more storage and increases replication overhead.
> 
> ## 13.6 Take advantage of Tez
> 
> Tez can reduce unnecessary intermediate writes and improve execution efficiency for suitable Hive queries.
>

> # Hive: LATERAL VIEW
> 
> The easiest way to understand **`LATERAL VIEW` is to connect it with `EXPLODE()`**, which we discussed while learning UDTFs.
> 
> ## 1. The problem
> 
> Suppose we have a Hive table called `students`:
> 
> |id|name|skills|
> |---|---|---|
> |1|Rahul|`['Python', 'Java', 'SQL']`|
> |2|Priya|`['Python', 'R']`|
> 
> We want to convert each student's array of skills into separate rows **while retaining the student's ID and name**.
> 
> We can use `EXPLODE()` with `LATERAL VIEW`.
> 
> ## 2. Syntax and example
> 
> ```
> SELECT
>     s.id,
>     s.name,
>     skill
> FROM students s
> LATERAL VIEW EXPLODE(s.skills) lv AS skill;
> ```
> 
> Let's understand each part:
> 
> |Component|Meaning|
> |---|---|
> |`students s`|Reads the table and gives it the alias `s`|
> |`EXPLODE(s.skills)`|Converts each array element into a separate row|
> |`LATERAL VIEW`|Applies the table-generating function to each input row and makes its generated rows available to the query|
> |`lv`|Alias for the generated virtual table|
> |`AS skill`|Names the generated output column `skill`|
> 
> ## 3. How does it work?
> 
> Imagine the first input row:
> 
> ```
> id = 1
> name = Rahul
> skills = ['Python', 'Java', 'SQL']
> ```
> 
> **Step 1:** `EXPLODE()` generates multiple rows.
> 
> ```
> Python
> Java
> SQL
> ```
> 
> **Step 2:** `LATERAL VIEW` associates these generated rows with the original row's columns.
> 
> ```
> 1  Rahul  Python
> 1  Rahul  Java
> 1  Rahul  SQL
> ```
> 
> The same process happens for Priya.
> 
> ### Final output
> 
> |id|name|skill|
> |---|---|---|
> |1|Rahul|Python|
> |1|Rahul|Java|
> |1|Rahul|SQL|
> |2|Priya|Python|
> |2|Priya|R|
> 
> Notice that the student's ID and name are repeated for each skill.
> 
> ---
> 
> ## 4. Why can't we just use `EXPLODE()`?
> 
> In Hive, `EXPLODE()` is a **UDTF (User-Defined Table-Generating Function)**. It generates rows from a collection.
> 
> `LATERAL VIEW` allows us to use that generated output alongside columns from the original table.
> 
> Think of it this way:
> 
> ```
> Original table
>       |
>       v
> Each input row
>       |
>       v
> EXPLODE(array_column)
>       |
>       v
> Generate multiple rows
>       |
>       v
> LATERAL VIEW
>       |
>       v
> Combine original columns
> with generated columns
>       |
>       v
> Final result
> ```
> 
> **Important distinction:**
> 
> - `EXPLODE()` generates rows.
> - `LATERAL VIEW` makes those generated rows available alongside the original row's columns.
>
